Control API

Other programs on the Mac can start and stop Quack dictation, and can receive the text instead of having it typed. For example, a game-controller app can start dictation when a button is pressed and finish it when the button is released. They can also list, add, change, and remove dictionary words. For example, a script can read a codebase and add its project names, so that Quack spells them correctly. To test Quack without a speaker and a microphone, a program can dictate an audio file, or replay one of the user's recent dictations.

There are three ways to connect:

InterfaceUse it for
The control socketApps that hold a session, receive text, claim dictation, or edit the dictionary.
quackctlScripts, agents, and languages that cannot open a Unix socket.
quack:// linksOne-shot triggers from Shortcuts, Stream Deck, or open.

Permission

The first time a program sends a request or opens a link, Quack asks: Allow “App” to use Quack dictation? Quack remembers the answer. To change it, open Settings › Connected apps. Turning an app off or removing it disconnects it. A removed app is asked about again the next time it sends a request.

Quack attributes a request to the nearest app that launched the process, as macOS privacy prompts do. A Python script run in Terminal counts as Terminal. quackctl run by your controller app counts as the controller app. A process that no app launched is identified by its executable path. The open command often exits before Quack can trace it, so links that Quack cannot trace share one permission: Links from unidentified apps.

The permission prompt asks for consent. It is not a security boundary between programs that run as the same user.

Voice commands that an app adds (register_commands, set_command, unregister_commands) have their own permission, and they never ask for or give the permission to control dictation. See App commands.

Control socket

Connect to the Unix domain stream socket at:

~/Library/Application Support/Quack/control.sock

Only the user who runs Quack can connect. If the socket is missing, Quack is not running, or has only just launched and is still opening it. Start Quack with open -g -b com.ericbellamy.Quack only when it isn't running, then retry: macOS turns open on a running Quack into a reopen, which shows Settings.

Each message is one JSON object on one line, ending with a newline (\n), in both directions. Requests are limited to 64 KB. A words reply can be longer. Quack ignores unknown fields. Clients must ignore unknown fields and unknown event types, because later versions can add them.

deliver sets where the text goes:

  • type (default): typed into the focused app, as with the shortcut.
  • return: sent only to your app. Nothing is typed, and Accessibility access is not needed.
  • both: typed into the focused app and sent to your app.

partials (default true) sends stable words while the user is still talking. It applies only when your app receives the text.

mute (default true) mutes playing speakers and headphones while Quack listens, as the shortcut does, and restores them afterward. Quack mutes only output devices that are playing, and never virtual or aggregate devices. It mutes nothing when the user turns off Settings › Mute audio while dictating. Set mute to false to keep audio playing, for example game sound. Quack can then hear audio from speakers through the microphone. For capture, mute applies to every dictation the claim receives.

Automated tests and agents must not mute the user's speakers. Set mute to false, or set QUACK_DISABLE_OUTPUT_SILENCING=1 in the environment of quackctl, which then sends false. To stop a test build of Quack from muting anything, launch it with that variable or with open -g Quack.app --args -QuackDisableOutputSilencing YES. Quack reads the microphone directly and never opens an output device, so dictation with muting off does not touch playback.

Session rules

  • One dictation runs at a time. While your app's dictation runs, the shortcut does not start or stop it. Esc still cancels it.
  • If your connection closes during your dictation, Quack cancels it. A crashed app cannot leave the microphone on.
  • In type and both modes, words appear in a pill while you speak. When dictation finishes, Quack pastes the complete transcript into whichever app has focus. Typing, clicking, and switching apps do not cancel dictation. Esc cancels it in every mode. In return mode, Quack sends text to your app without pasting it.
  • Quack shows its listening badge during every dictation. It mutes playing speakers unless the request set mute to false or the user turned muting off.

Capture

{"op":"capture","enabled":true} sends every dictation to your app, including dictation started with the shortcut or a link, and nothing is typed. The user's dictation arrives as started with source: "keyboard", then partial, final, and ended. You can stop or cancel it. The menu bar shows which app receives dictation.

One app at a time can hold the claim. It ends when you send {"op":"capture","enabled":false} or close the connection. Closing the connection during a captured dictation cancels that dictation.

Dictionary

A dictionary word is an object with term, the spelling Quack types, and heard_as, a list of ways the word gets misheard. Quack replaces each heard_as form with term. heard_as is optional in requests and can be empty. The forms are stored in lowercase, because matching ignores case. Settings shows them as Heard as.

No duplicates

Quack compares text the way it hears it: case, spaces, and punctuation are ignored. GitHub, github, and Git Hub are the same text, and so are cube control and Cube-Control. Each text belongs to at most one word, as its term or as one of its heard_as forms. Quack enforces this rule itself, so a client never has to check first:

  • Adding a word that is already in the dictionary keeps the existing spelling. The reply lists it in existing. New heard_as forms are added to it.
  • A heard_as form that sounds like the word itself, or like one of its other forms, is dropped. It adds nothing.
  • If another word already owns a term or form in an add, the owner keeps it. Quack skips that text, adds the rest of the request, and lists the text in ignored with the owning word. To move it, remove it from the owner with edit, then add it again.
  • edit rejects a rename or heard_as that another word owns, with exists, and changes nothing.

Repeating an add therefore changes nothing, so a script or agent can run again safely. Settings follows the same rule. When Quack starts, it removes duplicates that a dictionary saved by an earlier version can hold. Text stays with the first word that claims it, so corrections do not change. A word spelled like an earlier word merges into it.

→ {"op":"add","words":[{"term":"kubectl","heard_as":["cube control"]},{"term":"Tauri"},{"term":"Cube Control"}]}
← {"added":["kubectl","Tauri"],"event":"ok","existing":[],"ignored":[{"text":"Cube Control","word":"kubectl"}]}
→ {"op":"find","terms":["Cube-Control","tauri","Rust"]}
← {"event":"words","missing":["Rust"],"words":[{"heard_as":["cube control"],"term":"kubectl"},{"heard_as":[],"term":"Tauri"}]}
→ {"op":"words"}
← {"event":"words","words":[{"heard_as":["cube control"],"term":"kubectl"},{"heard_as":[],"term":"Tauri"},…]}

find takes a list of texts in terms. It replies with each word that owns one of them as its term or a heard_as form, once per word, and lists the texts no word owns in missing.

Changes

  • add puts new words at the top of the dictionary, in request order.
  • edit changes the word named by term. rename respells it, for example Github to GitHub. heard_as replaces all of its forms; [] removes them. Omitted fields stay the same.
  • remove removes the words whose terms match, and ignores the rest.
  • A term has at most 64 characters on one line, with at least one letter or digit. Quack trims surrounding whitespace and collapses inner whitespace. If one word is invalid, Quack rejects the whole request with bad_request and changes nothing.
  • Changes are saved, appear in Settings, and apply to the next dictation. A dictation in progress keeps the dictionary it started with.
  • Dates in replies are ISO 8601 text in UTC, such as 2026-10-18T21:42:39Z.

History

Quack keeps every dictionary change permanently, whoever made it: a person in Settings, the Add to Quack Dictionary service, an app through this API, or Quack itself when it removes duplicates. Each request that changes the dictionary is one change. quackctl add sends a long list as several requests, so it can make several changes.

{"op":"history"} replies with the changes, newest first. limit returns only the newest that many. Each change has these fields:

FieldMeaning
idCounts up from 1. Names the change in undo.
dateWhen it happened.
by, by_idSettings, Services menu, Learned from your fix, Quack, or the app's name, and the app's bundle ID or executable path when an app made it.
summaryA readable description, such as Added Tauri (heard as tory).
undoesThe change this one undid, if it is an undo.
changesEach word before and after: word_id, before and after (as in words replies; missing when the change added or removed the word), and index, the word's position before the change.

{"op":"undo","change":12} reverses change 12 as a new change, which can itself be undone. A removed word returns where it was. Quack refuses with conflict if a later change touched the same words, and names that change, so an undo never overwrites later work. Undo the later change first, or edit the word. Settings shows the history under Dictionary › History…, with an Undo button on each change.

→ {"op":"history","limit":1}
← {"event":"history","history":[{"by":"Terminal","by_id":"com.apple.Terminal","changes":[{"after":{"heard_as":["tory"],"term":"Tauri"},"index":0,"word_id":"7F0B…"}],"date":"2026-10-18T23:28:05Z","id":53,"summary":"Added Tauri (heard as tory)"}]}
→ {"op":"undo","change":53}
← {"event":"ok","history":[{"by":"Terminal",…,"id":54,"summary":"Undid change 53: Removed Tauri","undoes":53}]}

Usage

Quack counts how each dictionary word fires in the user's dictations, so that an agent can find words that never help and words that fire where they shouldn't. Quack counts only microphone dictations, not replays or audio files. {"op":"usage"} replies with one entry per word, in dictionary order:

FieldMeaning
word_id, termThe word.
usesDictations in which the word fired in any way.
spelledTimes the transcript spelled the word itself, perhaps with other case, spacing, or punctuation.
formsTimes each heard-as form fired, such as {"tory":3}.
near_missesTimes a word of six or more letters matched text a letter or two off, by the text heard, such as {"prism":2}. Ordinary words here are false matches.
steeredTimes dictionary biasing steered the speech model to the word.
last_used, sinceWhen the word last fired, and when Quack began counting it.
recordingsUp to five kept recordings in which it fired, newest first, to replay.
learnedIts heard-as forms that Quack learned from the user's fixes, when it has any.

The reply's fixes lists fixes the user made once, which Quack learns if they make them again, such as {"count":1,"date":"…","heard":"jean","term":"Jeanne"}, where count is how many times the user has made it. Quack learns each one if the user makes the same fix again. See Learning from your fixes.

A word that never fires costs almost nothing. A heard-as form or near miss that matches ordinary speech changes text the user meant, every time. To check one, replay its recordings, then edit or remove the word. History can undo the change if it was wrong.

Probe

Before adding a word, an agent can hear how Quack hears it. {"op":"probe","terms":["Tauri","Siobhan"]} has macOS speech synthesis say each word in three sentences, in the voices Samantha, Daniel, Karen, and Moira (American, British, Australian, and Irish English). Quack transcribes each sentence as dictation would with the word in the dictionary, and replies with what it typed in the word's place. It takes up to 20 words, about a second each, and changes nothing. Dictation keeps working meanwhile.

→ {"op":"probe","terms":["Tauri","Siobhan"]}
← {"event":"probe","probes":[{"clips":12,"heard":[{"count":6,"ordinary":true,"text":"tory"},{"count":2,"ordinary":true,"text":"torah"}],"right":4,"term":"Tauri"},{"clips":12,"heard":[{"count":3,"ordinary":false,"text":"chauvon"},{"count":2,"ordinary":false,"text":"chavon"}],"right":7,"term":"Siobhan"}]}
FieldMeaning
termThe word.
clipsSentences said, each in each installed voice.
rightClips in which Quack typed the word as spelled.
heardWhat Quack typed instead, most often first: text, lowercased as heard-as forms are stored, and empty when nothing was typed; count; and ordinary, true when every word of it is an ordinary English word.

Use it to choose heard-as forms. A form that is not a word, such as "chavon", rarely matches anything else the user says, so it is safe to add. A form marked ordinary, such as "tory", would turn every "Tory" the user says into Tauri. Leave it out, and let the user's fixes teach it, or ask the user. A word that is right in every clip needs no form.

A probe predicts real speech only roughly. The voices read the spelling, so a word spelled unlike it sounds, such as Vercel, is said wrong. They have no accent, and real speakers mishear in their own ways: on the accent benchmark (scripts/accent-eval), another speaker's most common misheard form matched about 7% of a speaker's misses with the dictionary on. A word the voices get right can still be misheard; the user's fixes catch those (see Learning from your fixes).

Large dictionaries

Quack handles dictionaries of 100,000 words. Correcting a transcript takes the same time at any size. Each change rebuilds the dictionary's indexes in the background, which takes about 25 ms at 25,000 words and 200 ms at 100,000. The change applies once the indexes are ready, so a dictation that starts within that moment can still use the previous dictionary. Settings lists the newest 200 words and searches the rest.

Size costs accuracy rather than speed. Every word is a chance for the speech model to be steered toward it, and every heard-as form rewrites the words it matches. Use usage to remove words that misfire.

The corner's target

While vibecoding, the screen's top-left corner shows where new threads go: a computer, a project, a model and an effort, which the user sets by voice ("change project to Quack"). Apps that show T3 Code's threads for that project, such as Bulletin, follow it.

Quack keeps it in a file, so following it needs no socket and no permission:

~/Library/Application Support/Quack/thread-target.json

Quack writes the file at launch, whenever the target changes, and when T3 Code names the computer or project or changes the project's title or color. It replaces the file in one step (written beside it, then renamed), so watch the folder or the path, not the file's inode. {"op":"thread_target"} and quackctl target reply with the same object.

FieldMeaning
version1. Raised only for changes that older readers would misread. New fields don't raise it.
computerid, T3's environment ID; label, the name T3 shows, missing until T3 has said it; local, true when it's this Mac, whose T3 server's port is in ~/.t3/userdata/server-runtime.json.
projectid, T3's project ID on that computer; title, workspaceRoot and color, missing until T3 has listed the project. color is one of T3's 18 color names (gray, red, … rose): the project icon's color, else the one T3 picks from the name.
modelprovider (claudeAgent, codex, …), slug, and name, as T3's picker shows it.
effortid as T3 sends it (high), missing for the model's default; label; level, 1 to 5.

A field is missing when the user hasn't chosen one yet.

Choosing the corner's project

An app that picks projects, such as Bulletin's tabs, can point the corner at one: {"op":"set_thread_target","project":"468afa91-…"}. project is T3's project ID. computer, T3's environment ID, is optional: without it, Quack looks for the project on the corner's computer first, then on the other computers it reaches. Moving to another computer keeps the model and effort where that computer offers them, as a spoken change does. The corner changes at once, and Quack rewrites thread-target.json before it replies.

Quack replies thread_target with the new target, not_ready when it isn't connected to T3 Code for threads, and not_found when no computer it reaches has the project. A dictation that is starting a thread keeps the target it showed when the dictation began. quackctl target PROJECT [COMPUTER] sends the same request.

→ {"op":"set_thread_target","id":"1","project":"468afa91-…"}
← {"event":"thread_target","id":"1","target":{"computer":{…},"project":{"id":"468afa91-…","title":"Quack",…},…}}

Showing a thread in the panel

An app that lists threads, such as Bulletin's Completed corner, can show one in the thread panel that vibecoding mode keeps in the bottom-left corner: {"op":"show_t3_thread","thread":"8f0c…"}. Sent for a thread the panel doesn't show, it switches T3 Code to that thread in the background, as clicking another thread's bubble does, and the panel follows it. Sent again for the thread the panel shows, it widens the panel to T3's chat width, and sent once more, it narrows the panel back to open. Repeating the request toggles between the two.

Quack replies once it's done: ok with panel set to switched, wide or open. It replies not_ready when the panel isn't on screen (vibecoding is off, T3 Code is in front, or the corner is withdrawn) or Quack can't switch T3 in the background (no Accessibility, or T3 isn't running), and not_found when Quack doesn't know the thread or T3's sidebar has no row for it. After either error, open the thread some other way, such as T3's own t3code://threads/ENVIRONMENT/THREAD link. quackctl threads show ID sends the same request.

→ {"op":"show_t3_thread","id":"1","thread":"8f0c…"}
← {"event":"ok","id":"1","panel":"switched"}
→ {"op":"show_t3_thread","id":"2","thread":"8f0c…"}
← {"event":"ok","id":"2","panel":"wide"}

Handing new threads to Bulletin

Here Quack is the client. Bulletin keeps a working queue: each project runs as many threads at once as Bulletin's Working tray has slots, and the rest wait in Bulletin's Queue. When the user says "new thread" and presses Return, Quack first offers the task to Bulletin (BulletinQueue), on Bulletin's socket:

~/Library/Application Support/dev.tired.bulletin/queue.sock

Bulletin answers only processes of the user who owns its data folder. One request per connection, one JSON object per line each way. target is the object thread-target.json holds, for the target the dictation started with; images are the dictation's screenshots, by absolute path. Bulletin copies them before it replies, so Quack may delete its own afterwards.

→ {"op":"queue_task","version":1,"id":"6F1C…","text":"Fix the tray\n\nThen the tabs","images":["/…/Screenshot 1.png"],"target":{"version":1,"computer":{…},"project":{"id":"468afa91-…",…},"model":{…},"effort":{…}}}
← {"event":"queued","id":"6F1C…","item":"q12","ahead":2,"starts":false}

queued means Bulletin has the task: item is its queue item, ahead how many of the project's queued tasks wait before it, and starts whether a working slot is free for it now. declined (reason: queue_off, other_computer, no_model, unknown_project, invalid or failed, with a message) means Bulletin won't run it, and Quack starts the thread in T3 itself, as it does when nothing listens on the socket. When Bulletin took the request but sends no answer within 8 seconds, Quack starts nothing, since Bulletin may have queued it, and says so in the agent card. {"op":"status","id":"1"} replies {"event":"status","id":"1","version":1,"workingQueue":true}.

"Ask an agent", "reply with", and routed tasks ("… in Bulletin") still go straight to T3. The Bulletin side is documented in Bulletin's desktop/src-tauri/src/features/quack_handoff/README.md; change both together.

Settings

{"op":"settings"} replies with a settings event: settings holds every setting the Settings window and the menu bar panel offer, by the name it has in Quack's settings.json, and choices.microphones lists this Mac's microphones (uid, name) for microphoneUID. A setting left unset, such as an automatic launcher, is null.

{"op":"update_settings","changes":{"sleepingDuckBrightness":0.3,"showsSleepingDuck":true}} changes the named settings. They apply at once and are saved, as when the user changes them in Settings; nothing restarts. Quack refuses the whole request with bad_request if a name is unknown or a value is of the wrong type, out of range, or not among a setting's choices, and the message says what the setting takes. Otherwise it replies ok with every setting afterwards.

quackctl settings describe lists each setting with what it does and the values it takes; the list lives in Sources/QuackCore/SettingsAPI.swift. The dictionary isn't a setting here; use its own requests. Which apps may control dictation can't be changed through the API, so no program can grant itself or another one access.

→ {"op":"update_settings","changes":{"sleepingDuckBrightness":0.3}}
← {"event":"ok","settings":{"sleepingDuckBrightness":0.3,"showsSleepingDuck":true,...}}
→ {"op":"update_settings","changes":{"sleepingDuckSpeed":10}}
← {"code":"bad_request","event":"error","message":"sleepingDuckSpeed can't be 10. Duck speed, as a multiple of normal speed. From 0.25 to 3."}

Voice commands

The user's own voice commands (Settings › Voice commands) are the voiceCommands setting, and three requests change one at a time:

RequestFieldsWhat it does

App commands

An app can add voice commands to Quack: phrases that, when the user says them, Quack reports to the app instead of typing. The app decides what each one does, and how Quack treats it: whether the dictation keeps going after it, whether it waits for Return, and where it works. A command can also name a link in the app's own URL scheme for Quack to open, so it works while the app is closed. Quack runs nothing else for an app. Any language that can open a Unix socket can use them, such as Node or Electron, Python, and Swift.

Use an app command for anything your app owns, rather than adding a command for the user with the MCP tool save_voice_command: an app command shows under your app in Settings › Voice commands, the user allows your app once, and you can change the commands later.

Allowing an app

The first time an app registers commands, Quack shows a pop-up. It lists each command's phrases, what the app says the command does, which commands can wake Quack, and any clash with a phrase that Quack already listens for:

  • Same phrase as a built-in command, one of the user's commands, or another app's command. The command is refused and shown unchecked. It can't be added unless one of the two is renamed. This includes a phrase that a built-in command or a target command hears as itself, such as "start a new thread" or "change model to opus", said alone or with words after it, because the built-in would always take it first.
  • Starts with another phrase, or sounds like one (one word apart, and that word sounds alike). This is a warning. The command stays checked.

The user can uncheck any command, then allows the app with Touch ID or their password. Quack adds the commands exactly as the pop-up showed them when the user pressed Allow. A command that the app registers while the pop-up is open shows at the top, unchecked, so the user allows it only after seeing it. A command that the app changes after the user presses Allow isn't added: Quack asks about the new version in a pop-up of its own. Quack checks the phrases again when the user allows them, so when two apps wait for the same phrase, only the first app the user allows gets it. Quack doesn't ask again for this app. After that, the app can do the following without asking:

  • Turn each command on and off, and turn each command's wake status on and off, as often as it likes.
  • Register new commands and change existing ones. They go straight in if they have no clash. A command with a warning-level clash waits for the user, in a pop-up that lists only those commands. A command with the same phrase as another is refused. Quack compares each command with the commands that will be in force after the request: when a change to a command is refused or waits for the user, the command's earlier version keeps its phrases, so another command in the same request can't take them.

Commands the user unchecked stay registered but off, and the app isn't asked about them again. The user turns them on in Settings › Voice commands, which lists every app's commands. There, the user can also turn off an app or a command, or remove an app, which then has to ask again. If the user chooses Don't allow, Quack refuses the app's commands until Quack restarts. Each app has one pop-up, which grows as the app asks for more; a program at the same path whose code has changed gets a pop-up of its own after it, saying its code changed. At most 8 apps can wait for the user at once: a request that would open a pop-up for another app fails with busy, and nothing in it is kept, so register the commands again later.

Quack knows an app by the code signature of the process that connects, not by the app that launched it. A signed app is known by its team ID and bundle ID when it has the hardened runtime. A helper inside it, such as an Electron renderer in Contents/Frameworks, counts as that app when the same team signed both and the app's resources, Contents/Resources/app.asar among them, still match its seal. Quack checks the seal only for a bundle of up to 200,000 files and 4 GB; a helper of a bigger app is known by its path instead, and so can't add commands (see below). Quack checks later connections against the app's designated requirement. A program that isn't a signed app with the hardened runtime, such as python3, node, or an ad-hoc signed build, is known by its executable's path, and the pop-up and Settings label it Unverified. Quack asks again when the program's own code changes: its executable, and for an app bundle or a helper inside one, the bundle's sealed resources too. When the bundle has no seal, or its resources no longer match it, Quack reads every file in the bundle's Contents instead, and where each symbolic link points. For a link, Quack hashes only its target path, not a file outside the bundle that it points to. An unverified program's grant needs all of its code: a bundle of more than 200,000 files or 4 GB, one with a folder Quack can't read, an executable bigger than 4 GB, or a file Quack can't read to its end is too big to fingerprint, and its command requests fail with not_allowed and the reason "Quack can't check this app's code: it's too large to fingerprint; sign it with Developer ID and the hardened runtime". Quack shows no pop-up for it. A signed app bigger than those limits is refused too, because Quack can't check it against its seal either. For an interpreter, Quack sees only the interpreter, not the script it runs: every script run by python3 or node at that path shares the grant and its commands, and changing the script doesn't ask again. An app started to run a script, as ELECTRON_RUN_AS_NODE or NODE_OPTIONS does, or with any DYLD_ variable in its environment, which can load other libraries into it, is unverified too. So is a process with an entitlement that lets other code into it despite the hardened runtime (com.apple.security.get-task-allow, com.apple.security.cs.disable-library-validation, com.apple.security.cs.allow-dyld-environment-variables or com.apple.security.cs.disable-executable-page-protection), and a process that is being debugged when it connects. Quack reads a process's arguments, environment and debugging state by its process ID, and counts them only if that ID still names the process that connected after the read; when it can't tell, the process is unverified. The JIT entitlements that Electron apps carry, allow-jit and allow-unsigned-executable-memory, don't make an app unverified. Quack checks a bundle against its seal once while it runs, and checks it again only when the bundle's files change. Sandboxed apps can't reach the socket. quackctl can't register commands, because it would register them as Quack.

The grant, the commands, and the user's switches are kept in Quack's keychain, not in settings.json, and the Settings API can't change them.

Requests

A connection can send at most 20 command requests a second, and all connections together at most 40; requests one connection sends past its own limit don't count toward the total. At most 32 connections that sent a command request can be open at once; a command request from another connection fails until one of them closes. Quack answers each refused request with a busy error that carries the request's id, and keeps the connection open. Quack reads the code signature of each connection once, at its first command request, and reads at most 16 at a time. A connection whose first command request arrives while 16 are being read gets a busy error with the request's id, and Quack closes it. Connect again later. Connections that only control dictation aren't counted. An error for a request that Quack can't read still carries the request's id when the id is a string.

register_commands takes commands, an array of up to 64 commands. An app can have at most 64 commands in all, counting those allowed and those waiting for the user; Quack refuses a new command past that, with a reason, until the app unregisters some.

FieldMeaning
idThe app's own name for the command, up to 64 characters. Unique among this app's commands. Each app has its own IDs, so an app can't change another app's commands.
phrasesWhat the user says, 1 to 8 phrases. Quack matches them without case, punctuation, a leading "hey Quack", or "please", "ok" and "okay" around them.
doesWhat the command does, in a sentence for the user. Required.
formalone (default): the phrase is the whole dictation. then_words: the phrase starts the dictation, and the words after it go to the app. A then_words phrase needs at least two words.
may_waketrue lets the app turn on the command's wake status, so saying it after a pause wakes Quack while a wake phrase is on. Each phrase then needs 2 to 4 words.
only_when_frontmosttrue makes the command count only while the app is the front app. Quack checks this itself. It needs an app bundle.
only_while_vibecodingtrue makes the command count only while vibecoding is on.
keeps_dictatingtrue keeps the dictation going after the command instead of ending it: Quack confirms the command with a chip, and what the user says next is dictated as usual, into whatever is focused once the command has run. Only a command heard while the user is still talking carries on; one heard when the dictation ends simply runs.
confirmstrue shows the command in Quack's card and waits for Return before running it. It ends the dictation, so it can't be combined with keeps_dictating.
opensA link that Quack opens in the app itself when the command is heard, instead of sending command_heard, such as "thoughtful://new". Its scheme must be one the app's Info.plist declares (CFBundleURLTypes), so it needs an app bundle. In a then_words command, {words} in the link's path or query is replaced by the words said after the phrase, percent-encoded. Quack opens the link even while the app isn't connected, which launches it, so the command stays on while the app is closed. Up to 2048 characters.
activeThe command's starting state. Default true.
wakeThe starting wake status. Default false. Needs may_wake, and the command active: Quack refuses a command with "active": false and "wake": true.

Quack replies with a commands event: granted lists the commands that are in, refused lists {"id","reason"} for the commands it won't take, and pending lists the commands waiting for the user. When the user answers, Quack sends another commands event, without id, for those commands. Registering a command again with the same definition changes nothing that the user allowed, and resets its starting state, so register every command each time the app connects.

set_command takes command, the command's ID, and active, wake, or both. It replies ok. A command wakes Quack only while it is active, so setting active to false also turns its wake status off, and turning the command on again leaves wake off until the app sets it. It fails with not_found if the app has no such command, and with bad_request if wake is true for a command registered without may_wake, or for a command that would be off: send "active": true with it. It works for commands still waiting for the user, so their state is ready once allowed. When a changed version of an allowed command waits for the user, set_command sets both versions, and each takes wake only if it was registered with may_wake. So the allowed version keeps waking while a version without may_wake waits, and a waiting version with may_wake doesn't make the allowed version wake.

unregister_commands takes ids, or removes all of the app's commands if ids is left out. It replies ok, with removed listing the commands removed.

Hearing commands

A command is live while its app is connected, the user has the app and the command switched on, the app has it active, for an only_when_frontmost command the app is in front, and for an only_while_vibecoding command vibecoding is on. A command with opens is also live while its app isn't connected, with its wake status off. Only a connection that Quack has matched to the app's grant can set active and wake on an allowed command. Before the user allows the app, the state that a request sets waits with the commands and applies when the user allows them. An app can have more than one connection open. When the app's last connection closes, every one of its commands goes off: active and wake return to off, and the app sets them again when it reconnects. When two live commands could both match, the command of the app in front wins, then the user's commands, then other apps' commands.

When the user says one, Quack checks again that the command is live. For a command with opens, it opens the link in the app and sends nothing. Otherwise it sends the event to the app's connection that sent a request most recently, and to no other client:

← {"event":"command_heard","frontmost":true,"id":"next","phrase":"next slide","words":""}

phrase is the phrase as registered. words holds what was said after a then_words phrase, and is empty otherwise. frontmost says whether the app was in front.

Quack decides that an app is in front by the front app's bundle ID and executable together. A signed app is in front when the front app has its bundle ID and runs from inside its bundle, so another app that claims the same bundle ID doesn't count. An unverified program is in front only when the front app's executable is the program's own executable.

Keep the connection open to receive events. Don't half-close it, as shutdown(SHUT_WR) or Node's socket.end() do: Quack then treats the app as finished, closes the connection once it has replied, and turns the app's commands off.

Example: Node or Electron

const net = require("net");
const os = require("os");
const readline = require("readline");

const socket = net.connect(`${os.homedir()}/Library/Application Support/Quack/control.sock`);
const send = (request) => socket.write(JSON.stringify(request) + "\n");

socket.on("connect", () => send({
  op: "register_commands", id: "r1",
  commands: [
    { id: "next", phrases: ["next slide"], does: "Shows the next slide.", may_wake: true },
    { id: "find", phrases: ["find slide"], does: "Finds a slide by its title.", form: "then_words", only_when_frontmost: true },
  ],
}));

readline.createInterface({ input: socket }).on("line", (line) => {
  const event = JSON.parse(line);
  if (event.event === "commands") console.log("in:", event.granted, "waiting:", event.pending, "refused:", event.refused);
  if (event.event === "command_heard" && event.id === "next") nextSlide();
  if (event.event === "command_heard" && event.id === "find") findSlide(event.words);
});

// While a presentation plays, let "next slide" wake Quack.
function presenting(on) { send({ op: "set_command", command: "next", wake: on }); }

In Electron, run this in the main process, so it connects as the app. A helper process inside the app also counts as the app.

MCP server

quackctl mcp is an MCP server on standard input and output, so agents such as Claude Code and Codex can use Quack as tools: get_settings and update_settings, list_voice_commands, save_voice_command and remove_voice_command, get_status, and the dictionary's list_words, find_words, add_words, edit_word, remove_words, probe_words, dictionary_history, undo_dictionary_change and word_usage. Each tool sends the request of the same purpose above over the control socket, starting Quack if it isn't running, so the first call from an agent asks for permission like any other app. Add it to Claude Code with:

claude mcp add --scope user quack -- /Applications/Quack.app/Contents/MacOS/quackctl mcp

and to Codex in ~/.codex/config.toml:

[mcp_servers.quack]
command = "/Applications/Quack.app/Contents/MacOS/quackctl"
args = ["mcp"]

The tools are defined in Sources/QuackCore/MCPTools.swift and served by Sources/quackctl/MCP.swift.

Testing with audio

start can play audio instead of listening to the microphone. Set one of these fields:

  • audio: the absolute path of an audio file that macOS can read, such as WAV, AIFF, M4A, or FLAC.
  • recording: the id of a kept recording.

Quack plays the audio at the speed it was spoken, so partials and the pill behave as they do for speech. Dictation finishes at the end of the audio, and the events are the same as for the microphone. You can stop or cancel it sooner. Playing audio needs no Microphone access and does not mute audio output. Quack does not record pace for it or keep it as a recording. Use deliver: "return" so that nothing is pasted into the focused app.

→ {"op":"start","deliver":"return","audio":"/tmp/test.aiff"}
← {"deliver":"return","event":"started","session":7,"source":"client"}
← {"event":"partial","session":7,"text":"Deploy with"}
← {"action":"type","event":"final","session":7,"text":"Deploy with Tory."}
← {"event":"ended","reason":"finished","session":7}

Kept recordings

Quack keeps the user's last 1,000 dictations, and each new one replaces the oldest. The audio is compressed losslessly, so a 10-second dictation takes about 190 KB and a thousand take about 200 MB. Recordings kept before 1.14.1 are not compressed. Each recording is encrypted with a key in the user's keychain, so only Quack can play it. Quack keeps a dictation only after it is transcribed into some text.

{"op":"recordings"} replies with the kept recordings, newest first; {"op":"recordings","limit":50} with the newest 50. Each one holds everything Quack knew about the dictation:

FieldMeaning
idNames the recording in start.
date, secondsWhen the dictation finished, and the length of its audio.
heardThe model's transcript, before Quack removed a voice command and replaced heard-as forms. The dictionary has already biased the model toward its words.
wordsThe words of heard, each with its start and end in seconds.
text, actionWhat Quack delivered, and type, send, or scratch, as in the final event.
routing_vocabularyCatalog computer, model, and project names used as recognition hints. Replays retain this snapshot. Absent on older recordings and dictations without routing hints.
screen_wordsNames and terms read from the window Quack typed into, which biased the dictation besides the dictionary. A replay of the recording uses the same ones.
uncleanedThe text before Clean up text tidied it into text. Present only when cleanup changed the text.
source, client, appWhat started the dictation (keyboard, link, or client), the app that controlled it or received its text, and the bundle ID of the app Quack typed into. Each of the last two is present only when it applies.
pageThe top-level web page in the focused window when a typing dictation started, when Accessibility exposes it. Contains domain and an optional title, for example {"domain":"mail.google.com","title":"Inbox - Gmail"}. URL paths, query strings, fragments, and credentials are discarded. Captured even when screen words are off. Absent for return-only dictations and older recordings.
microphone, peak_dbThe microphone, and the loudest sample in dB below full scale. Near 0 means clipping. Below about -30 means the microphone heard the speaker faintly.
model, quack_versionThe speech model revision and the Quack version.
correctionsEach dictionary word that changed the text, in order: its term, its kind (term, form, near_miss, screen for a term shown on screen, name for a project, model or app name capitalized, or steered), the form that fired, and the heard words it matched.
dictionary_changeThe newest dictionary change when the dictation finished. history up to it gives the dictionary that was in use.
→ {"op":"recordings"}
← {"event":"recordings","recordings":[{"action":"type","app":"com.apple.Terminal","corrections":[],"date":"2026-10-18T21:42:39Z","dictionary_change":41,"heard":"Deploy the app with Tori and Vaughn.","id":"20261018T144239","microphone":"MacBook Pro Microphone","model":"Phonon-2-1143812f…","peak_db":-9.5,"quack_version":"1.5.3 (18)","seconds":3.69,"source":"keyboard","text":"Deploy the app with Tori and Vaughn.","words":[{"end":0.52,"start":0.21,"text":"Deploy"},…]}]}

When the user says that Quack misheard a recent dictation, an agent can fix the dictionary and check the fix:

1. Find the dictation by its text or heard. 2. Replay it with start and recording to see what Quack hears now. 3. add the right words, with the misheard text from heard as heard_as. If heard is right and text is wrong, a heard-as form made the mistake: edit that word. 4. Replay it again. The dictionary applies to the next dictation, so the replay shows the fix.

If an earlier change made the mistake, for example a heard-as form that rewrites an ordinary word, find it with history and reverse it with undo.

Example

A controller button that dictates into a chat field inside your app:

→ {"op":"start","id":"a","deliver":"return"}
← {"deliver":"return","event":"started","id":"a","session":4,"source":"client"}
← {"event":"partial","session":4,"text":"Meet at the"}
→ {"op":"stop"}
← {"event":"ok"}
← {"action":"send","event":"final","session":4,"text":"Meet at the north gate."}
← {"event":"ended","reason":"finished","session":4}

Minimal Python client:

import json, os, socket

sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
sock.connect(os.path.expanduser("~/Library/Application Support/Quack/control.sock"))
events = sock.makefile("r")

def send(**request):
    sock.sendall((json.dumps(request) + "\n").encode())

send(op="start", deliver="return")
input("Talk, then press Return. ")
send(op="stop")
for line in events:
    event = json.loads(line)
    if event["event"] == "final":
        print(event["text"], event["action"])
    if event["event"] in ("ended", "error"):
        break

quackctl

quackctl is inside the app at /Applications/Quack.app/Contents/MacOS/quackctl. Quack also links it into a folder on the shell's PATH: ~/.local/bin if that folder exists, otherwise /opt/homebrew/bin or /usr/local/bin. Quack updates the link when the app moves, and never replaces a quackctl that is not its own. Running the app itself from a shell, as in Quack.app/Contents/MacOS/Quack --help or Quack recordings, runs quackctl. If Quack is not running, quackctl starts it in the background. If Quack is running but its socket doesn't answer yet, as in its first moments after launch, quackctl waits up to 10 seconds instead of opening it again (Sources/quackctl/Launch.swift).

quackctl --help begins with the steps for fixing a word that Quack mishears. The Recordings folder in ~/Library/Application Support/Quack holds a README.txt that points to the same commands.

quackctl status                             # Prints the status event.
quackctl dictate                            # Prints the final text. Return or end of input finishes.
quackctl dictate --deliver type             # Types into the focused app instead.
quackctl dictate --json                     # Prints every event as a JSON line.
quackctl dictate --no-mute                  # Keeps audio playing while listening.
quackctl dictate --audio test.aiff          # Dictates a file instead of the microphone, and prints the text.
quackctl dictate --recording 1              # Replays the newest kept recording. Also takes an ID.
quackctl connect-t3                         # Connect Quack to T3 locally, without a browser or pasted code.
quackctl threads                            # Lists the T3 Code threads with a colored bubble: ID, reason, project and title.
quackctl threads connect                    # Connects Quack to T3 Code for thread bubbles. `disconnect` undoes it.
quackctl threads open ID                    # Brings T3 Code forward at that thread. Ask the user first.
quackctl threads show ID                    # Shows that thread in the thread panel, or widens or narrows the panel. Ask first.
quackctl recordings                         # Lists the newest 50 kept recordings: number, ID, date, length, and what Quack heard and typed.
quackctl recordings --all                   # Lists every kept recording.
quackctl recordings --cleaned               # Only the dictations Clean up text changed, with the text before it, from every kept recording.
quackctl recordings --unknown               # Only dictations with words that are neither English nor a term Quack knew of, which are often mishearings.
quackctl recordings --since 1.16.0          # Only dictations made with that version of Quack or a later one. Combines with the other filters.
quackctl recordings --json                  # Prints every detail of each recording.
quackctl capture                            # Prints every dictation as JSON lines until Ctrl-C.
quackctl connect                            # Relays JSON lines between standard input and the socket.
quackctl words                              # Prints the dictionary, one word per line.
quackctl find "cube control" Tauri          # Prints the words that own each text. Exits 1 if any is missing.
quackctl add Tauri Bun                      # Adds words, and prints what it added and skipped.
quackctl add kubectl --heard-as "cube control" --heard-as "cube cuddle"
quackctl edit Github --rename GitHub        # Respells a word.
quackctl edit kubectl --heard-as "cube cuddle"  # Replaces its heard-as forms. --no-heard-as removes them.
quackctl remove Tauri Bun                   # Removes words.
quackctl history                            # Lists the newest 50 dictionary changes. --all lists every one.
quackctl undo 53                            # Reverses change 53.
quackctl usage                              # Shows how often each word fired, and how. --unused lists words that never fired.
quackctl probe Tauri Siobhan                # Prints what Quack types when macOS voices say each word. --json prints the reply.

dictate reads standard input: any input, or the end of input, finishes dictation. With --audio or --recording, it ignores standard input and finishes at the end of the audio. A relative --audio path is resolved against the current directory. Ctrl-C, SIGTERM, or SIGHUP cancels it. To drive it from another program, start quackctl dictate with a pipe as standard input when the button goes down. Write a newline when it comes up to finish, or terminate the process to cancel. Exit status: 0 finished, 1 error, 2 usage error, 3 cancelled.

words prints a word with heard-as forms as kubectl = cube control, cube cuddle. Without words as arguments, add and remove read one word per line from standard input, in the same format. quackctl words > words.txt saves the dictionary, and quackctl add < words.txt restores it. Long input is sent as several requests. add prints the words it added, the words already in the dictionary, and each text it skipped because another word owns it. --json prints Quack's replies instead. The other changes print nothing when they succeed. Every dictionary command exits with status 1 and a message when Quack refuses a request.

An agent can hear a word before adding it, and add only forms that are safe:

quackctl probe Siobhan
# Siobhan: right in 7 of 12
#    chauvon ×3
#    chavon ×2
quackctl add Siobhan --heard-as chauvon --heard-as chavon

probe marks forms made of ordinary words, such as "tory" for Tauri. Adding one would rewrite those words whenever the user says them.

An agent can also test a fix without playing sound, for example with a clip made by say:

say -o /tmp/test.aiff "Ask Siobhan about it"
quackctl dictate --audio /tmp/test.aiff     # Ask Chavon about it.
quackctl add Siobhan --heard-as chavon
quackctl dictate --audio /tmp/test.aiff     # Ask Siobhan about it.

An agent or script can fill the dictionary from a project, for example with names from package.json:

jq -r '.dependencies // {} | keys[]' package.json | quackctl add
